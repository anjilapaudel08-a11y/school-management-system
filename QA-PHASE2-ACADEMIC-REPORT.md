## Defects found and resolution

1. **School settings did not load or update — Medium (P2), fixed.** `SchoolForm` initialized empty and never loaded `/api/school`; saving an existing record returned 409. The form now loads the configured school, surfaces load/save errors, and POST updates the existing row or creates one only when none exists. The API validates name, email, URL, and established year.
2. **Reversed academic-year dates were accepted — Medium (P2), fixed.** Client and API now reject end dates before start dates. The UI shows a validation message, the API returns 400, and no invalid retest year persisted.
3. **Duplicate academic-year handling returned HTTP 500 — Medium (P2), fixed.** The API now maps Prisma unique violations to HTTP 409 with a clear conflict message.
4. **Unordered school selection could target the separate billing school — High (P1), fixed for school settings, academic years, classes, teachers, and student collection/creation routes.** These routes now use `getPrimarySchool()`, ordered by creation time and ID. During retesting, the wrong-school year was created as a test artifact; it had no dependents and was deleted by exact ID. Post-fix API counts and duplicate requests confirmed the primary-school scope.

## Addendum: finalized school decisions (2026-11-23)

The school finalized the previously open section decision after Phase 2. Sections are **not required** operationally. No section-management workflow or enrollment section selector should be added. The Phase 2 observation that new student registration permits a null `sectionId` remains accurate; preserve the existing section records and section-linked enrollment history.

Source review found no student UI/API use of `sectionId` and no `/api/sections` route. The remaining explicit dependencies are the nullable `Enrollment.sectionId` foreign key and index, the `Section` model/relation, and section references in `prisma/seed.ts`, `prisma/seed-results.ts`, and `scripts/qa/reset-and-seed.ts`; generated Prisma artifacts also reflect the current schema. Do not remove any of these in Phase 3. A separate cleanup proposal should inventory every existing link, retain or archive historical associations as approved, update seed/reset tooling, and use a reviewed migration if schema removal is eventually approved.

The following requirements and classifications are now explicit:

- **Required:** academic-term date boundaries. The current `AcademicTerm` model has no start/end fields. Implement and validate them in a separate academic-management follow-up, unless a direct student-management dependency is demonstrated.
- **Required:** multiple teacher/class/subject assignments, with exact-duplicate prevention and valid class-subject relationships. The current `TeacherAssignment` compound key includes teacher, class, subject, and academic year; the API requires an existing class-subject relation and the UI submits independent assignments. Phase 3 will perform regression checks without changing the existing behavior.
- **Not required:** routine academic-year editing. The app has no year edit UI/API; any exceptional correction must first assess dependents and use a controlled, auditable path.
- **Desirable:** teacher, class, and subject activation/deactivation, currently absent from their models/UI.
- **Existing limitation:** in-app password change/reset/recovery is not implemented. Preserve the future ADMIN/ACCOUNTANT permission specification and comprehensive non-ADMIN authorization backlog; neither is in Phase 3 scope.

The maintained classification and implementation queue are in [QA-TEST-INVENTORY.md](./QA-TEST-INVENTORY.md) and [SCHOOL-ACADEMIC-FOLLOW-UP-BACKLOG.md](./SCHOOL-ACADEMIC-FOLLOW-UP-BACKLOG.md). This addendum does not alter the historical Phase 2 results, authorize a schema change, or change any QA data.
